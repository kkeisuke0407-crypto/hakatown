## 1. 設計思想

### 1-1. これはSEO記事ではなく、広告の着地点

- 前置きを書かない。検索した人の疑問に**最初のH2で答える**
- 目次を置かない。SEO目的の長文化をしない
- キーワードを不自然に繰り返さない
- 「読ませる」より「**迷いを1つずつ外す**」

### 1-2. 買わせるのではなく、判断の順番を変える

このLPの中心にある発想。

```
× 種類を決めてから、霊園を探す   ← 読者が今やっていて、しんどい方法
○ 候補を見てから、種類を決める   ← 提案サービスを使うと選べる方法
```

**サービスを褒める前に、読者の今のやり方が大変な理由を言語化する。**
そのうえで「順番を逆にできる」と示し、それができる手段としてサービスを出す。

この「認識転換」が入口と出口をつなぐ背骨。ここが弱いと、
どれだけサービスを褒めても「ふーん」で終わる。

### 1-3. 検索意図ごとに入口だけ変え、以降は共通化

14本の横展開LPで運用できることを確認済みの構造。

```
可変（検索意図ごと）          固定（全LP共通）
─────────────────    ──────────────────────
FV / H1                      教育パート（選択肢の整理）
FVティザー                    自力でやる大変さ
導入2文                       認識転換
最初のH2とその本文             サービス登場 → メリット → CTA
                             信頼 → 事例 → 使い方 → 比較 → FAQ → 最終CTA
```

- 可変部は **全体の15%程度**。ここだけ書けば1本増える
- 固定部はマスター1か所で管理し、生成スクリプトで配る
- 共通部の見出しは**検索意図への回答ではなく、全KW共通の教育パート**として使う

## 2. 構成（section順）

実装は `index.html`。IDと役割は次のとおり。

| # | id | 役割 | 可変/固定 | 見出しの例 |
| --- | --- | --- | --- | --- |
| 1 | `fv` | ファーストビュー | **可変** | H1＋ティザーカード＋導入2文 |
| 2 | `points` | 検索への即答 | **可変** | まず見るのは、この4つ。 |
| 3 | （同上） | 選択肢の教育（H3） | 固定 | お墓は、大きくこの4つ。 |
| 4 | `hard` | 自力でやる大変さ | 固定 | これ、自分でやると結構大変です。 |
| 5 | `turn` | 認識転換（山場1） | 固定 | どのお墓にするかは、あとで決めればいい。 |
| 6 | `service` | サービス登場（山場2） | 固定 | ＼それができるのが／＋サービス名 |
| 7 | （同上） | 褒め本文＋✅4行＋CTA | 固定 | — |
| 8 | `trust` | 運営元の信頼 | 固定 | どんな会社がやってるの？ |
| 9 | `cases` | 事例・利用者の声 | 固定 | 使った人は、こう決めています。 |
| 10 | `steps` | 操作画面 | 固定 | やることは、5つだけ。 |
| 11 | `vs` | 自力との比較（山場3） | 固定 | 自分で探すか、候補から選ぶか。 |
| 12 | `faq` | 不安の払拭 | 固定 | よくある質問 |
| 13 | `close` | クロージング | 固定 | まず、候補を見てみる。 |

### 順番の理由

- **2→3**：検索意図に即答したあと、すぐ「選択肢はこれだけある」と視野を広げる。
  ここで広げておかないと、後段の「種類はあとでいい」が効かない
- **4→5**：大変さを見せてから転換する。**転換の前に必ず痛みを置く**
- **5→6**：転換の方法として初めてサービスを出す。ここまでサービス名を出さない
- **6→7**：サービス定義のあと、褒めるのは1か所にまとめる。分散させない
- **8→9**：褒めたあとに必ず裏取り（運営元→実例）を置く
- **11**：最後にもう一度「自力 vs 提案」を並べて、選択を明確にする

### CTAの位置（5本）

`service` 直後 / `trust` 末尾 / `cases` 末尾 / `steps` 末尾 / `close`。

`data-cta` の値は設置位置を表す（`service` `trust` `cases` `operation` `final`）。
GA4が `cta_position` にこの値を送るので、**既存値を使い回さない**。

## 3. FVの作り方

```
┌──────────────────────────────┐
│                 ※注記（右上・白チップ）│
│ アイキャッチ文                        │
│                                      │
│ H1（2〜3行、写真の上）                 │
│                                      │
│  ┌────────────────────────┐  │
│  │ ティザー見出し（緑・太字）        │  │
│  │ ティザー本文（黄マーカー）        │  │
│  │ ［ ↓ どんな探し方か見てみる ］    │  │
│  └────────────────────────┘  │
└──────────────────────────────┘
```

### 決まりごと

- **写真に文字を焼き込まない。** すべてHTMLテキスト。差し替えが効くこと優先
- **H1はまず1行で自然に読める長さを狙う。** `<span>` は意味のまとまりとして使い、CSSでは `display:inline`。横幅に収まるなら1行、収まらないときだけ自然に折り返す
- 見出し・事例タイトルには、レイアウト目的の `<br>` を原則入れない。入る幅では1行、狭い幅ではCSSに自然に折り返させる
- 長いH1は `.ohaka-hero--h1-m` で一段小さく
- ティザー見出しは文字数で自動的にサイズを落とす（`--m` 21〜30字 / `--s` 31字〜）
- FVの高さは固定（スマホ512px）。コピーが長いLPだけ `hero: 'tall'` で伸ばす
- **H1とティザーカードの間隔は最低12px。** 切ると事故る（QAで自動検出）

### 写真のトリミング

縦長に切り抜かれるので、**元絵の幅の半分強しか映らない**。
人物が片側に寄っている写真は `object-position` で寄せる。
PCは切り抜きがほぼ発生しないので、モバイルだけ指定する。

## 4. デザイン規則

### 4-1. 色の役割（`:root` の変数）

| 用途 | 変数 | 値 |
| --- | --- | --- |
| ブランド緑（見出し・CTA） | `--gold` `--cta` | `#176b65` `#167063` |
| 濃い緑（山場・CTA下線） | `--cta-bottom` | `#0c4e46` |
| **赤（サービス名だけ）** | `--hot` `--hot-bg` | `#c9372c` `#ffd8d2` |
| 見出しマーカー | `--mk` | `#cbe6da` |
| 本文マーカー | `--marker` | `#fff3ad` |
| 注記 | `--note` | `#767676` |
| 矢印・記号 | `--arrow` | `#3a7a69` |
| 金額・特典の文字 | `--accent-txt` | `#946416` |

**重要：線・面用の色を文字に使わない。**
`--gold-line` `--accent` は薄いので、文字に使うと白地で読めなくなる。
文字用に `--arrow` `--accent-txt` `--note` を別に用意してある。

**赤はサービス名の1か所だけ。** ここを守るから、スクロール中に赤が
1回だけ出てくるのが効く。他に赤を足すと全部死ぬ。

### 4-2. 見出しの階層

形で区別する。サイズだけで区別しない。

| 階層 | 見た目 |
| --- | --- |
| 大見出し（h2） | 緑マーカー ＋ **記事幅いっぱいの下線4px** ＋ 上に小ラベル |
| 山場の大見出し | 同上、下線を5pxの濃緑に |
| 補足の章（FAQ） | マーカーなし、下線2pxの細線 |
| **サービス名** | **赤マーカー ＋ 赤の下線4px**（中央寄せ） |
| 中見出し（h3） | 緑の小さな四角 ■ を頭に置く |

- **大見出しは1行に収まるなら1行。** 無理に固定改行せず自然に折り返す。変な1語・1文字残りになる場合は文言を短くする
- 見出しの上の小ラベル（`sec-eyebrow`）は4〜11文字。章の役割を言う
- 下線は章の区切り線も兼ねるので、罫線を別に引かない

### 4-3. 強調

- 1セクションに「大声」は1回まで
- 黄マーカー（`em-green`）も**1セクション1回**
- `<strong>` は文末の結論句に寄せる
- 全文を太字にしない。太字だらけは太字がないのと同じ

### 4-4. 動き

| 対象 | 動き |
| --- | --- |
| 章頭 | 視界に入ったらラベル→見出し→下線の順にふわっと（1回だけ） |
| サービス名 | 同上、下線は中央から左右に伸びる |
| CTA | 光沢が0.9秒かけて通り過ぎ、2.7秒休む（無限ループ） |

- 動かすのは `transform` と `opacity` だけ。**レイアウトを動かさない**（CLSゼロ）
- 隠す指定は `<html class="js-reveal">` が付いたときだけ有効。
  このクラスは IntersectionObserver があり、かつ
  `prefers-reduced-motion: reduce` でない場合だけ head で付与する
- **JS無効でも内容が必ず見えること。** ここを外すと本文が消える

### 4-5. 注記

- 11.5px / `--note #767676`（白地でコントラスト比4.54:1）
- **これ以上薄くしない。** 読めない注記は表示している意味がない
- 本文2段落の間に挟まない。図のキャプションか、セクションの末尾に置く

## 5. 文体

### 基本

- **やさしい日本語。** 1文は短く、修飾を重ねない
- 話し言葉に寄せる（「これ、自分でやると結構大変です。」）
- 専門語は使った直後に言い換える
- 読者を責めない。「調べ方が悪い」ではなく「調べる作業が大変」

### 断定を避ける

広告基準の話であると同時に、信頼の問題。

| 使わない | 使う |
| --- | --- |
| いちばん選ばれています | 今回の調査では最も多く選ばれています |
| いちばん抑えられます | 抑えやすい傾向があります |
| 〜が要らなくなります | 〜の手間を減らせます |
| 〜のほうが早い | 〜のほうが考えやすくなります |

**根拠のない「No.1」「最大級」は追加しない。**

### 章から章へのつなぎ

各章の終わりに1行だけ「渡し」を置く（`.bridge`）。

- 中央寄せ、本文より小さいグレー、下に ↓
- **次の章の問いを先に出す**（「とはいえ、どこが運営しているのか。」）
- CTA直後にも置く。クリックしない人がそのまま読み進められる

## 6. 法務・広告基準

### 必ず入れる

| 項目 | 場所 |
| --- | --- |
| PR表記 | FV直下 |
| ※本記事中の画像はイメージです。 | FV右上 |
| ※本記事の金額・内容は一例です。 | FV右上 |
| ※本記事ではAI生成画像を使用しています。 | フッター |
| 運営者名＋運営者情報ページ | フッター |
| 数値の出典＋確認日 | その数値のすぐ近く |

### 入れない

- **申込可能な社数**（「1社でも構いません」等）
- **金額レンジを前面に出す**（FV・H1に「5万〜150万円」等）
- 根拠のない最上級表現
- 広告主が禁止する領域（補助金・助成金など案件ごとに確認）

### 数値の扱い

- 出典・調査時点・母数・「全国平均ではない」旨を必ず添える
- **数値を消したら、その出典注記も消す。** 対象を失った注記は残さない
- 金額を出す場合は「エリアや種別が異なる場合も含まれる」旨を添える

## 7. 横展開のやり方

### 原則

**共通部は `index.html`、各LP固有部は `tools/lp_data.py` を正本にして、`tools/build_lp.py` で配る。**
生成済みの横展開LP（`<slug>/index.html`）は直接編集しない。直接編集すると次の生成で消える。

### 手順

```bash
# 1. 新しいLPのコピーを tools/lp_data.py に足す
# 2. 生成
python3 tools/build_lp.py
# 3. コピーと共通部の照合
python3 tools/verify_copy.py
# 4. 表示検査
node tools/qa_lp.mjs '["slug-a","slug-b"]'
```

### `tools/lp_data.py` に書くもの

```python
{
 'slug': 'near-reien',           # URL（/near-reien/）
 'name': '近くの霊園',
 'kw': '近くの霊園',              # data-keyword に入る
 'title': '…',                   # H1と食い違わせない
 'desc': '…',
 'eyebrow': '近くで探すなら',      # 見出しの上の小ラベル
 'h1': ['近くの霊園、', '距離だけで', '選んで大丈夫？'],  # 1要素＝意味のまとまり。改行固定ではない
 'ttl': '…',                     # ティザー見出し（1文目）
 'txt': '…',                     # ティザー本文（残り）
 'intro': ['…', '…'],            # 導入2文
 'h2': '「近い」と「通いやすい」は、同じではありません。',
 'body': [('p','…'), ('list',[…]), ('note','…')],
 # 任意：'h1_size':'m' / 'hero':'tall' / 'hero':'tall-xs'
}
```

### 共通部の見出しを変えたとき

`index.html` にある共通部先頭のH3文言と、`tools/lp_data.py` の `FIXED_MARK` を**セットで直す**。
`FIXED_MARK` は生成・検査が共通部の開始位置を見つけるための目印なので、実際のH3と必ず一致させる。

## 8. 検査

**目視だけで確認しない。** コピー・H1/H2・CSS・HTML構造・画像配置のどれかを触ったら、必ず機械検査を通す。

| スクリプト | 見るもの |
| --- | --- |
| `tools/verify_copy.py` | コピーの一致、共通部がマスターと同一か、計測タグの欠落 |
| `tools/qa_lp.mjs` | 横スクロール、はみ出し、FVの重なり、画像切れ、CTA数、演出の生存 |

### 検査幅

`320 / 360 / 375 / 390 / 414 / 820px`

### 過去に検査をすり抜けた失敗

**演出の「効いていること」を、結果だけで判定しない。**

スクロールイン演出の検査を「隠れている見出しの数」で見ていたため、
演出CSSごと消えたときに0件＝正常と判定してしまった。
いまは **CSSの存在そのもの**（`transition` が生きているか、
マーカーの色が想定値か）を確認している。

**CSSをまとめて削除するときは、削除範囲にほかのブロックが
挟まっていないか必ず確認する。** これで一度、サービス名の赤ハイライトと
全章の演出を巻き添えで消している。

## 9. 新規案件の始め方

```bash
cp -r template/ ../new-project/
cd ../new-project/
```

`template/README.md` の手順に従う。差し替えるのは次の6つ。

1. `styles.css` の `:root` の色（ブランドに合わせる）
2. `index.html` の各セクションの中身
3. 画像一式
4. CTAの遷移先・`data-cta`・GA4のID
5. `tools/lp_data.py` の横展開コピー
6. `about/index.html` の運営者情報

**構成・見出しの階層・検査スクリプトは変えない。**
ここを変えると品質が再現できない。
