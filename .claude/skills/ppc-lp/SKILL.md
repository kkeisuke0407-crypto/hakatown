# PPC記事LP の作り方

タウンライフお墓マッチのLP（マスター1本＋検索意図別の横展開14本）で確立し、
運用できることを確認した作り方。次の案件でも同じ品質を出すための土台。

## 最初にやること

**現物があるなら、本書より現物を見る。** 抽象的な規則より実装が正。

| 作業場所 | 見るもの |
| --- | --- |
| hakatown リポジトリ | `docs/LP-PLAYBOOK.md` `docs/LP-CHECKLIST.md`、`index.html`、`townlife-ohaka/styles.css`、`tools/` |
| 新規案件 | `template/` をコピーして始める。`template/README.md` に差し替える6項目 |
| このスキル単体 | `references/` の3ファイル（下記） |

`references/structure.md`（構成と順番の理由）、
`references/design.md`（色・見出し・動き・FV）、
`references/compliance.md`（文体・広告基準・検査）。
**該当する作業に入る前に、対応するファイルを読むこと。**

---

## 1. これは何を作る仕事か

**SEO記事ではなく、広告の着地点。** 読者は広告をクリックして、
何か困りごとを抱えて来ている。だから、

- 前置きを書かない。検索した人の疑問に**最初のH2で答える**
- 目次を置かない。SEO目的で長くしない
- キーワードを不自然に繰り返さない
- 「読ませる」のではなく「**迷いを1つずつ外す**」

## 2. 中心にある発想：判断の順番を変える

このLPが効く理由はここに尽きる。

```
× 種類を決めてから、霊園を探す   ← 読者が今やっていて、しんどい方法
○ 候補を見てから、種類を決める   ← 提案サービスを使うと選べる方法
```

**サービスを褒める前に、読者の今のやり方が大変な理由を言語化する。**
そのうえで「順番を逆にできる」と示し、それができる手段としてサービスを出す。

この「認識転換」が入口と出口をつなぐ背骨。
ここが弱いと、どれだけサービスを褒めても「ふーん」で終わる。

**新しい案件でまず決めるのは、この1行。**
「読者が今やっている、しんどい順番」と「ひっくり返した順番」を
言葉にできていないなら、まだ書き始めない。ユーザーと詰める。

## 3. 骨格（13セクション）

順番には理由がある。詳細と理由は `references/structure.md`。

```
FV（可変）
検索への即答 H2（可変）
  └ 選択肢の教育 H3（固定・ここから共通）
自力でやる大変さ           ← 転換の前に必ず痛みを置く
認識転換（山場1）           ← ここまでサービス名を出さない
サービス登場（山場2）        ← 褒めるのはこの1か所に集約
  └ 褒め本文＋✅4行＋CTA
運営元の信頼               ← 褒めた直後に裏取り
事例・利用者の声
操作画面
自力との比較（山場3）
FAQ
クロージング＋最終CTA
```

CTAは5本（サービス直後／信頼末尾／事例末尾／操作末尾／クロージング）。
`data-cta` は設置位置ごとに違う値にする。GA4が `cta_position` に
この値を送るので、既存値を使い回すと計測が混ざる。

## 4. 横展開の考え方

**検索意図ごとに入口だけ変え、サービス登場以降は全KW共通にする。**
可変部は全体の15%程度。ここだけ書けば1本増える。

正本の置き場所を間違えないこと。

| 何 | 正本 |
| --- | --- |
| 共通部 | `index.html` |
| 各LP固有部（FV・最初のH2） | `tools/lp_data.py` |
| 生成物 `<slug>/index.html` | **正本ではない。直接編集しない** |

生成済みLPを手で直すと、次の生成で消える。これは実際に起きた事故。

```bash
python3 tools/build_lp.py                      # 生成
python3 tools/verify_copy.py                   # コピー・共通部の照合 → NG 0
node tools/qa_lp.mjs '["slug-a","slug-b"]'     # 表示検査 → 問題なし
```

共通部の先頭H3の文言を変えるときは、`index.html` のH3と
`tools/lp_data.py` の `FIXED_MARK` を**セットで直す**。
`FIXED_MARK` は生成・検査が共通部の開始位置を探す目印なので、
実際のH3と一致していないと両方とも止まる。

## 5. デザインで絶対に崩さない3つ

詳細は `references/design.md`。ここだけは先に頭に入れておく。

1. **赤はサービス名の1か所だけ。** ページ内で赤が出てくるのが1回きりだから、
   スクロール中にそこで目が止まる。他に赤を足すと全部死ぬ
2. **線・面用の色を文字に使わない。** 薄い色（`--gold-line` `--accent`）を
   文字に使うと白地で読めなくなる。文字用の色が別に用意してある
3. **見出しはサイズでなく形で区別する。**
   大見出し＝マーカー＋幅いっぱいの下線、中見出し＝緑の■。
   サイズだけで差をつけても、流し読みでは区別できない

## 6. 文体

**やさしい日本語。** 1文は短く、話し言葉に寄せる。
読者を責めない（「調べ方が悪い」ではなく「調べる作業が大変」）。

断定は避ける。広告基準であると同時に、信頼の問題。

| 使わない | 使う |
| --- | --- |
| いちばん選ばれています | 今回の調査では最も多く選ばれています |
| いちばん抑えられます | 抑えやすい傾向があります |
| 〜が要らなくなります | 〜の手間を減らせます |
| 〜のほうが早い | 〜のほうが考えやすくなります |

根拠のない「No.1」「最大級」は**足さない**。

章の終わりには渡しの1行を置く（次の章の問いを先に出す）。
CTA直後にも置くと、クリックしない人がそのまま読み進められる。

## 7. 広告基準

`references/compliance.md` に一覧。特に落としやすいのは、

**必ず入れる**：PR表記／画像はイメージ／金額は一例／AI生成画像の明示／
運営者名とリンク／数値の出典・調査時点・母数。

**入れない**：申込可能な社数（「1社でも構いません」等）／
FV・H1に金額レンジ／根拠のない最上級。

**数値を消したら、その出典注記も消す。** 対象を失った注記が残っていると
読み手に意味が通らない。これも実際に起きた。

## 8. 検査

**目視だけで確認しない。**
コピー・見出し・CSS・HTML構造・画像配置のどれかを触ったら機械検査を通す。
検査幅は `320 / 360 / 375 / 390 / 414 / 820px`。

過去に検査をすり抜けた失敗を2つ、頭に入れておく。

- **演出が効いていることを、結果だけで判定しない。**
  「隠れている見出しの数」で見ていたため、演出CSSごと消えたときに
  0件＝正常と判定した。CSSの存在そのものを確認する
- **CSSをまとめて削除するとき、削除範囲に別のブロックが挟まっていないか確認する。**
  これでサービス名の赤ハイライトと全章の演出を巻き添えで消したことがある

公開前は `docs/LP-CHECKLIST.md`（なければ `references/compliance.md` の
チェック項目）を上から通す。

## 作業の進め方

1. **認識転換の1行を決める**（読者の今の順番 → ひっくり返した順番）
2. 可変部（FV・最初のH2）を書く。固定部は流用する
3. `build_lp.py` で生成 → `verify_copy.py` → `qa_lp.mjs`
4. チェックリストを上から通す
5. 直すときは**正本**（`index.html` か `lp_data.py`）を直して再生成

**構成の順番・見出しの階層・検査スクリプトは変えない。**
ここを変えると品質が再現できない。逆に言えば、
ここさえ守れば案件が変わっても同じ水準が出る。
